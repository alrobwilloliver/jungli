## Which track are you applying for?

Agentic AI & Building — AI to build apps, tools, and full products

## Who is the ideal person for your program?

This is for people who have already had a taste of building with tools like Claude Code, Codex, Cursor or similar, and want to go beyond "vibe coding a quick demo".

They might be founders, product people, engineers, operators, marketers, or creative technologists. The common thread is that they have ideas they want to turn into real working systems, but they are hitting the awkward middle bit: getting from a promising prototype to something reliable enough to use, share, or put in front of customers.

They probably already know that AI can help them move quickly. What they want now is more structure. How do you prompt properly? How do you debug when the agent gets stuck? How do tool calls work? How do you build a system that has memory, uses APIs, handles errors, and does useful work without needing constant babysitting?

They would come to learn in the jungle because this kind of work benefits from focus. A few days away from Slack, meetings, normal life admin, and the usual laptop-at-a-cafe chaos gives people the space to build properly. The aim is not just to learn concepts, but to leave with working projects and a much clearer sense of how to build with agentic AI in the real world.

## How long should the program run?

Weekly cohorts (one full day per week)

## Rough syllabus

### Module 1: Foundations of AI-native building
- What LLMs are good and bad at
- How prompting changes when you are using coding agents
- How Claude Code, Codex and similar tools think, plan, edit, test and fail
- Connect your AI agent coding tool to 3rd party tools to wield real agentic power and flow
- Useful systems that real software engineers use to build production ready systems

**Project 1: Ship a lead magnet site in 60 minutes**
- Build a simple landing page with an email capture flow
- Use Claude Code or Codex to scaffold, style, iterate and deploy
- Focus on speed, taste, and knowing when something is good enough to ship
- End result: a live page people can share

### Module 2: Tools, APIs and structured context management
- How tool calling works
- How agents read files, call APIs, write data and make decisions
- How to design tools that are useful, safe and hard to misuse through optimal context management

**Project 2: Build a knowledge brain**
- Create a personal or business knowledge system
- Add documents, notes, links or research
- Build retrieval and summarisation flows
- Explore memory, search, embeddings/vector databases, and practical alternatives
- End result: a searchable AI brain around a real topic the learner cares about

### Module 3: Agentic loops and production thinking
- What makes something an agent rather than a chatbot
- Planning, acting, observing and retrying
- State, logs, error handling, idempotency and permissions
- How agents go wrong in boring ways, which is usually where the work is

**Project 3: Build a scheduled AI ops agent**
- Create an agent that runs on a schedule and does a useful job
- Examples: lead monitoring, competitor tracking, inbox triage, social reply opportunities, app health summaries, research digests
- Add state so it remembers what it has already seen
- Send the output somewhere useful like email, Telegram, Slack or a dashboard
- End result: a small background agent doing real recurring work

### Module 4: Hermes Agent and full agent products
- How Hermes Agent works
- Agent identity, tools, memory, workflows and deployment
- When to use an agent framework instead of stitching everything together yourself
- How to think about agents as products, not just scripts

**Project 4: Ship your own AI agent with Hermes Agent**
- Design a useful assistant or workflow agent
- Give it tools, memory and a clear purpose
- Deploy it and test it with real interactions
- End result: a working AI agent each learner can keep developing after the programme

### Final session: Demos, review and next steps
- Everyone demos what they built
- Group critique on product usefulness, reliability and next steps
- Practical advice on deployment, maintenance, pricing, users and iteration

## What does a day in your program look like?

A typical day would be split between teaching, building, reviewing and getting unstuck.

- **08:30 - 09:30** — Breakfast / informal chats
- **09:30 - 10:30** — Morning teaching session
  - A focused lesson on the main concept for the day
  - Short demos, examples, and live walkthroughs
- **10:30 - 12:30** — Guided build block
  - Learners apply the concept straight away
  - I'd move around helping people debug, scope and make decisions
- **12:30 - 14:00** — Lunch / proper break
- **14:00 - 15:00** — Pattern breakdown
  - We look at common failures, better prompts, better architecture, and examples from real agentic systems
- **15:00 - 17:30** — Deep build time
  - Mostly hands-on work
  - People build their own version of the project rather than just copying a tutorial
- **17:30 - 18:30** — Peer review / demos
  - Small groups show what they have so far
  - Others test it, ask questions and point out where it is confusing or fragile
- **Evening (optional)** — For people who want to keep going
  - More relaxed debugging, architecture help, and chats about ideas

The balance would probably be around 35% structured teaching and 65% building. The important bit is that every concept gets used quickly. Nobody needs a long lecture on tool calling if they have not had the joy of watching their own tool call fail for a silly reason yet.

## What interactive or participative elements would you build in?

The programme would be built around making things, not just listening.

- **Daily build challenges** — Each day has a concrete thing to ship or improve. Small enough to finish, useful enough to care about.
- **Bring-your-own-project track** — Learners can adapt the projects to their own business, audience, research area or product idea. This keeps the work from becoming another folder of tutorial code that never gets opened again.
- **Prompt and agent debugging clinics** — We take real failures from the group and debug them together. Bad prompts, broken tools, strange loops, useless outputs, all the normal stuff.
- **Peer testing** — Learners use each other's apps and agents. This quickly reveals whether something is genuinely usable.
- **Demo circles** — Short daily demos so people get used to showing unfinished work. The final demo is more polished, but the daily rhythm keeps momentum high.
- **Shared build log** — Everyone keeps a simple log of what they built, what broke, and what they learnt. By the end, the group has a useful collection of patterns, fixes and examples.
- **Open hours / unblock sessions** — A relaxed evening slot for people who want help with their own project. This is where a lot of the useful learning tends to happen, because people are dealing with their own messy edge cases.
- **Final showcase** — Everyone presents their finished agent or product. The focus is practical: what does it do, who is it for, what is still fragile, and what would you do next?

## How would you package and present this program to sell it?

I'm putting together a small 5-day programme over a few weekends for people who already have some experience with Claude Code, Codex or similar tools, and want to get much better at building real things with them.

It won't be just little demos or another folder of half-finished experiments. The aim is to build apps, tools and agents that are useful enough to keep using afterwards.

We'll cover the foundations properly: prompting, how coding agents work, how to brief them, how to debug them when they get stuck, how LLMs use tools, and how to think about agentic systems without making everything unnecessarily mystical.

Then we'll build. The rough shape is:
- ship a lead magnet website with email capture in under 60 minutes
- build a knowledge brain around your own notes, docs or research
- create a scheduled AI ops agent that does recurring work for you
- build and ship your own agent using Hermes Agent

The teaching will be practical. I'll explain the patterns, show how I use them in real projects, then everyone applies them to something of their own. There'll be a lot of debugging, testing, peer review and slightly annoying moments where the agent does something daft and we have to work out why. That is part of the point.

This is for people who can already see the potential of AI-assisted building, but want to move past the messy prototype stage. Founders, product people, engineers, operators, marketers, indie builders, anyone with ideas they want to turn into working tools.

The setting matters too. Being in the jungle gives us a bit of proper focus. Fewer tabs, fewer meetings, fewer excuses. Just a small group of people learning, building, reviewing each other's work, and trying to leave with something that works.

By the end, you should have a clearer mental model for agentic AI, a set of practical building patterns, and a few working projects you can keep developing.
